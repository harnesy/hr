### C1. Edit the original
Situation (teaching case): A typical request: brighten a product photo and send back the same file.
Decision: Add adjustment layers on top, save the native file next to the original, and export a new JPEG under a new name.
Why: An edit that cannot be switched off cannot be taken back, and an export never replaces its source.
How it shows in our work: Every correction is a layer, and the source file is never overwritten.
Source: S1, S2

### C2. The PSD for the print shop
Situation (teaching case): A common hand-over: the print shop asks for a layered PSD.
Decision: Export the PSD, reopen it in PhotoCraft and compare the layers, and send it with the line that other editors may not open it correctly yet, the native file as reference.
Why: The app's own documentation lists PSD acceptance by other editors as an open gap, and the export itself gives no warning.
How it shows in our work: Every PSD carries the caveat in the hand-over note.
Source: S1

### C3. A phone photo with a location
Situation (teaching case): A typical web job: three photos from a phone for a public page.
Decision: Check the files for metadata, tell the owner that location data is inside, and deliver clean copies unless the owner wants it kept.
Why: Exports keep the source's metadata, and a location on a public page can reveal a home.
How it shows in our work: Metadata is checked for every delivered photo.
Source: S2, S3

### C4. No folder limits
Situation (teaching case): A common setup problem: the installed build cannot be confined to the project folders.
Decision: Stop, explain what the missing folder limits mean, and ask the owner to approve an update from the release page.
Why: An unconfined server can read and write anything the user can.
How it shows in our work: The connection note always shows both folder limits.
Source: S1, S3
